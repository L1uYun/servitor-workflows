servitor & servitor-workflows

两个用 Rust 编写的本地 agent 进程传输层与编排层

servitor 是一个 Rust 传输层：它接受一次请求，启动一个 provider 进程，固化证据，再返回一个小型类型化结果。工作流策略、扇出、角色、advisor 提示、schema 校验、Git 交付与任务验收都不属于它。

servitor-workflows 是构建在 servitor 之上的 Rust 编排层：它负责动态工作流执行、并发、命令、人工 gate、持久化状态、重放、暂停、取消以及机器运行证据。读者面交付报告是工作流输出，而非 Rust 渲染的运行时页面。

这两个工具是什么

它们是一对分工明确的 Rust 工具，一个负责「把一次任务可靠地交给某个 agent 进程」，另一个负责「把这些任务编排成有状态、可恢复的多步工作流」。

servitor：传输层

servitor 是一个本地 agent 进程的 传输层（transport layer）。它的职责被刻意收得很窄：接收一个请求，启动一个 provider 进程，把过程证据持久化下来，最后返回一个体积很小、带类型的（typed）结果。它只管「一次请求 → 一次 provider 调用」这一层。

它明确地不管工作流策略、任务扇出（fan-out）、角色分工、advisor 提示、schema 检查、Git 交付以及任务验收——这些都属于它之上的工具。换句话说，servitor 是地基，不是整栋楼。它解决的核心问题是：让「调用一个本地 agent」这件事变得可观测、可重放、可追溯，而不是一次性的黑盒命令。

日常用法很直接：用 servitor submit 提交一个 prompt（来自文件或直接字符串），立刻拿到一个持久的 RUN_ID 句柄；之后用 servitor get 读取（可等待），用 servitor list 盘点，用 servitor gc 清理卡住的运行，用 servitor cancel 请求终止。每一次运行都会在状态目录里留下 request.json、record.json、stdout.txt、stderr.txt 等证据文件。

servitor-workflows：编排层

servitor-workflows 是构建在 servitor 之上的 Rust 动态工作流运行时。servitor 在「一次 provider 调用」处刻意停下，而多步执行、并发、命令执行、人工审批（gate）、持久化状态、重放/恢复、验收以及机器运行证据，全部交给 servitor-workflows。

它解决的核心问题是：当一个真实任务需要「发现 → 并行审计 → 汇总」「需求 → 派发 → 独立评审 → 多重 gate → 回写」这类多步、带分支、带人工决策、并且中途崩溃后还能接着跑的流程时，靠单次 servitor 调用是不够的——需要一个有状态的编排器来管理调用身份、预算、边界审计和恢复。

它的执行契约由三个原语组成：agent + command + gate，分别对应「调用 agent」「执行命令」「等待人类决策」。工作流用沙箱化的 JavaScript 编写（Rust 二进制内嵌 Boa 引擎，不依赖 Node/Deno/V8/Python），因为普通的循环、分支和动态扇出在脚本里比静态 DAG 更清晰。脚本本身没有直接访问文件系统或进程的 API，所有外部工作都必须穿过 agent、command 或 gate 这些有类型的边界。

一句话概括：servitor 是「一次可靠的 agent 调用 + 持久证据」，servitor-workflows 是「把这一个个调用编排成可恢复、有预算、有边界的完整工作流」。

职责边界：谁拥有什么

servitor 与 servitor-workflows 是上下层关系：servitor 是 Rust 传输层，接受一次请求、运行一个 provider 进程、固化证据、返回一个小型类型化结果；servitor-workflows 是建在 servitor 之上的 Rust 编排层。两者各自拥有清晰的职责，也各自刻意不拥有一些东西。下表基于两份 README 列出对比。

维度servitor（传输层）servitor-workflows（编排层）
拥有agent 进程提交（submit）、检查（get/inspect）、取消（cancel）、输出固化（runs/RUN_ID/ 下的 request.json、record.json、stdout.txt、stderr.txt）；provider 适配器（pi、codex、codebuddy、claude）；image 生成/编辑传输；worker 心跳与进程存活上报（activity.status）；SDK 的 submit/get/cancel/inspect/list_runs/gc_runs。动态工作流执行、并发、命令（command()）、人机 gate（gate()）、持久化状态、replay/resume、暂停/取消、子工作流树、预算账本（budget.jsonl）、边界审计（boundary.jsonl）、能力注册与路由、事件流（events.jsonl）与 watch 树视图、机器运行证据 run-summary.html。
刻意不拥有多步执行、fan-out、命令、角色、advisor prompt、schema 检查、Git 交付、任务接受、replay/resume、人机 gate、报告渲染——这些属于 workflows。servitor 刻意停在“一次可持久的 provider 调用”。没有 advisor 子命令，专家咨询只是经现有传输表达的角色。不含 provider 适配器本身（仍经 servitor 提交）；不做模型兜底——显式 provider/model 选择不会被静默替换，不可接受的选择在提交前失败；不做静默重试 provider 或切换 provider；不设 token 预算停跑（token 仅用于归因，从不停止 run）；不渲染读者面向的交付报告（run-summary.html 仅是机器运行证据，读者报告由工作流报告阶段用 reader-centered-reporting + l1uyun-surface 产出）；不做内核级沙箱（边界审计只观察记录，不在内核层隔离）。
执行原语一次 SubmitRequest → 一个 provider 进程 → 一个类型化结果。三个原语：agent + command + gate；用沙箱化 JavaScript 表达循环、分支、动态 fan-out（内嵌 Boa，无 Node/Deno/V8/Python 运行时依赖）。
对协议的无知servitor 自身不感知工作流阶段与报告策略。workflows 不感知 provider 进程内部行为，只通过 servitor 的运行 id 复用已完成的调用。

一句话总结：servitor 负责“把一次 agent 调用可靠地跑完并留下证据”，servitor-workflows 负责“把多次调用、命令与人机决策编排成可恢复、可审计、有预算约束的完整工作流”。两者的边界由 README 明确写出，不可越界。

三个执行原语

servitor-workflows 的执行契约只有三个原语：

agent + command + gate

工作流用沙箱化的 JavaScript 编写，因为普通的循环、分支和动态 fan-out 在脚本里比静态 DAG 更清晰。Rust 二进制内嵌了 Boa 引擎；Node、Deno、V8、Python 都不是运行时依赖。

agent — 一次模型调用

agent(prompt, options?) 向 transport 提交一次模型调用。当请求结构化输出时，运行时会从模型自由文本里提取 JSON（剥离推理包装 → 收集候选片段 → 尾逗号修复 → 按 schema 形状过滤 → schema 合法性筛选，多个合法候选取最后一个），再做 schema 校验；若仍失败，会在同一个逻辑 journal 调用下补发一次修正请求，要求返回裸 JSON。默认 agent 是 pi。

const found = await agent("Find files to audit.", {
  schema: {
    type: "object",
    required: ["files"],
    properties: {
      files: { type: "array", items: { type: "string" } },
    },
  },
});

可用的 agent 选项包括 label、agent、model、cwd、systemPrompt、timeoutSeconds（默认 120）、nativeArgs、schema。给 pi 指定 model 时用 provider/model-id 格式（如 "newapi/glm-5.2"），provider 前缀必须匹配 ~/.pi/agent/models.json 的 providers 键；裸 model id（如 "glm-5.2"）会让 pi 猜测上游 provider 并以 No API key found 失败。

command — 一个本地命令

command(program, args?, options?) 运行一个本地命令，返回结构化的 CommandResult。在 Windows 上子进程不创建控制台窗口；stdout 与 stderr 各保留有界 1 MiB 尾部。

const r = await command("pwsh", ["-File", "flaky.ps1"], {
  label: "test",
  cwd: null,
  timeoutSeconds: 300,
  env: {},
});
// r: { argv, cwd, exitCode, stdout, stderr,
//      stdoutTruncated, stderrTruncated, timedOut, durationMs }

同一个结果对象会原子地持久化到 state/servitor-workflows/runs/<run_id>/commands/<key>/result.json，成功、非零退出和超时都同样落盘。直接消费这些类型化字段即可，不要重新读控制台输出或加一个 "read-results" 阶段。stdout/stderr 是有界尾部，不是业务结论——要回传机器判定，worker 应在约定路径写一份显式 evidence JSON。

gate — 暂停等人决策

gate(question, options?) 为一个人工决策暂停。除了 yes/no，gate 还可以带一个注入值用于"人工修正输入"的情形：

const fixed = await gate("give the correct contractPath", {
  expect: "value",                 // 请求一个 JSON 值而非 yes/no
  current: { contractPath: "old.md" },
  hint: "should be under surveys/",
});
await command("pwsh", ["-File", "check.ps1", fixed.value.contractPath]);

运行会停在 waiting_human 状态，expect/current/hint 写入 waiting_gate。收集这个值（聊天回答、本地决策页）是 controller 的工作；用 approve RUN_ID --reason TEXT --value '{"contractPath":"surveys/new.md"}' 注入，get 会返回已存储的值。

边界：JS 没有直接文件系统/进程 API

JavaScript 没有直接的文件系统或进程 API。任何外部工作都必须穿过类型化的 agent、command 或 gate 边界。这条约束与 journal 的确定性回放假设一致：脚本每次执行必须产生相同的调用输入，因此 Date.now()、Math.random()、无参 new Date()、以及把 Date() 当函数调用都会在脚本里抛 TypeError；时间戳和随机量应通过 args 传入（如 args.startedAt），并在工作流返回后再打墙钟时间。new Date(explicitValue)、Date.parse(...)、Date.UTC(...) 仍然合法。

控制流原语

README 把 servitor-workflows 的执行契约收敛为三个原语：agent + command + gate。围绕这三个原语，脚本里可用的控制流由一组全局函数提供。下面逐个给出作用与 README 中明文列出的选项。

pipeline(items, ...stages)

把一组条目按阶段串联推进，每个阶段对前一个阶段的产出再加工，常用于动态扇出的逐项处理（如对每个文件依次审计）。README 示例为 pipeline(found.files, file => agent(`Audit ${file}.`, { label: file }))。

parallel(promises)

并发执行一组 agent/command 调用并等待全部完成，是独立扇出与 section 组装的基础。README 的 intro-html 示例即用 parallel() 并行拼装各段 HTML。

retry(fn, options?)

对任意 agent/command thunk 做有界重试。每次尝试都是一次独立的 journaled call，尝试编号写入 journal key，因此重试不破坏确定性 replay：成功的尝试在 resume 时跳过，失败的尝试重跑。retry() 的墙上时间记账用隐藏 host clock，不喂入 call key，故不受确定性禁令影响。选项（README 原文）：

{
  maxAttempts: 3,          // fixed attempt cap
  delayMs: 2000,           // first backoff delay
  backoff: 2,              // multiplier (1 = fixed interval)
  wallTimeSeconds: 60,     // total elapsed cap (SLA), stops even if attempts remain
  nonRetryable: ["validation"], // fail fast when error text matches; no retry
}

gate(question, options?)

暂停运行以等待一个人类决策。除 yes/no 外，gate 还能为“人类修正输入”这一情形注入一个值：运行停在 waiting_human，把 expect/current/hint 写入 waiting_gate；控制器收集到值后用 approve RUN_ID --reason TEXT --value '{...}' 注入，get 会返回已存储的值。

supersede(options)

当方向本身错误时，把整个 run 标记为终态 superseded（区别于 failed/cancelled），并把 {reason, evidence?, newContract?} 记录进 state。控制器读 get 看到 status=superseded，写 supersede-chain 说明，再启动一个新 run——这是 continue-as-new，绝不就地改脚本。CLI 等价：supersede RUN_ID --reason TEXT [--evidence PATH] [--new-contract TEXT]。

workflow(path, args?, options?)（子工作流）

把另一个 workflow 脚本作为当前 run 的子运行执行。子工作流构成持久化的结构化并发树：每个 child 有自己的 run id、journal 与边界，同时共享 root 的并发调度器与预算账本。README 明文规则：

  • child 继承 parent 的 budget、boundary、capabilities 与 isolation，且只能收紧、不能放宽；
  • child 失败只 reject 那一次 workflow() 调用，由 parent 脚本决定策略（catch / retry / fail the chain）；
  • 人类等待沿树可见地上浮：批准 root 即恢复等待中的后代；
  • 循环与无界递归在任何 dispatch 之前被拒绝；
  • cancellation 从 parent 传播到所有存活后代。

这正是“独立审查”的表达方式：reviewer 作为带自身收窄（read-only）边界的 child workflow 运行，maker 的产出不会在同一个 run 里被自我打分。

一个真实可运行的示例

下面这段 workflow 脚本直接取自 README 里的 audit-routes 示例，展示了两个核心习惯：用 phase(name) 划分阶段，用 agent(prompt, options?) 让模型返回结构化结果，再用 pipeline(items, ...stages) 对上一步的结果做动态 fan-out。

每个 workflow 必须声明 meta.contract: "workflow"，否则在创建 run 目录之前就会被拒绝。agent 调用里给出的 schema 是 prompt 层契约，运行时会从模型文本里抽取 JSON 并按 schema 做有效性筛选；若抽取后仍不满足 schema，引擎会在同一逻辑 journal 调用下补发一次 correction 请求。

export const meta = {
  name: "audit-routes",
  contract: "workflow",
};

phase("discover");
const found = await agent("Find files to audit.", {
  schema: {
    type: "object",
    required: ["files"],
    properties: {
      files: { type: "array", items: { type: "string" } },
    },
  },
});

phase("audit");
const results = await pipeline(
  found.files,
  file => agent(`Audit ${file}.`, { label: file }),
);

return results;

README 给出的真实运行命令是直接指向 examples 目录下的 dynamic.workflow.js。这是一个可复制即用的命令：

servitor-workflows run D:\AgentWork\tools\servitor-workflows\examples\dynamic.workflow.js

运行前可以用 servitor-workflows check WORKFLOW.js 只做校验而不执行；run 自身也会做同样的校验，脚本无法解析时以 exit 2 拒绝，且不会创建 run 目录。提交后立即拿到 run_id，用 servitor-workflows get RUN_ID --wait 轮询直到成功、终态失败、取消、superseded 或 waiting_human。每个终态 run 都会生成机器运行证据 run-summary.html，注意它不是面向读者的交付报告。

持久化与恢复

servitor-workflows 把每个 run 的全部可恢复事实落到磁盘，进程崩溃或被杀后无需内存状态即可重建。默认状态根是 D:\AgentWork\state\servitor-workflows，可用 SERVITOR_WORKFLOWS_STATE_ROOT 覆盖。每个 run 独占一个目录 runs/<RUN_ID>/，内含下列文件：

  • workflow.js — 该 run 执行的工作流脚本本体，resume 时原样重放。
  • state.json — 运行状态机当前值与终态审计信息；cancel 的 --reason 文本以 error: "cancelled: <reason>" 形式记录于此。
  • journal.jsonl — 稳定调用身份与对应的 Servitor run id。已结算的调用在 resume 时从 journal 取回，不再向 transport 重提交；失败的调用在同一稳定身份下重跑。schema_correction 元数据会保留两个 transport run id 与校验错误，一次 correction 耗尽即终态，resume 不会提交第三次 transport run。
  • events.jsonl — 版本化、只追加的事件流：每次生命周期迁移、调用、gate、budget 变动、boundary 事件都追加一行。watch 完全从该流重建整棵树的实时视图（状态、活跃 phase、预算用量、等待类别、关键路径、恢复命令），不持有任何内存状态。重建时拒绝畸形或撕裂的事件尾部，仅容忍最后一条撕裂行作为崩溃痕迹。被杀后重启的 controller 能从事件重建出同一棵树，从第一个未完成调用继续。
  • budget.jsonl — 多维预算账本：调用数、可选金额、token 用量。记账走 预留→结算→释放，崩溃在预留与结算之间既不重复计费也不丢预留；resume 不发放新额度，重放 journaled key 免费。max_calls（CLI --max-calls，默认 1000）是全树硬上限；meta.moneyCap（分）仅在契约显式给出时才成为硬限；token 仅作归因、永不叫停。
  • boundary.jsonl — boundary 审计证据。契约可前置声明 readPaths/writePaths/network/environment.allow，host 对每条 command 比对声明并记录；未声明的写、越权的环境继承、子 run 放宽权限都会记为违例并阻断成功。这是审计边界而非内核级沙箱。journal 永不存凭据明文——密钥经 allowlisted 环境变量穿过，在 journal 中被脱敏。
  • run-summary.html — 每个终态 run 都拥有的自包含机器/运行证据页，由 Rust 从持久化 state 与 journal 生成，绝不打开浏览器。它是运行证据，不是面向读者的交付报告；读者交付报告由工作流 reporting 阶段用 reader-centered-reporting + l1uyun-surface 产出，Rust 仅在 workflow 返回指向已存在非空文件的绝对路径时才接受 report 字段。
  • pause.request / cancel.request — pause 与 cancel 的请求落盘文件，支撑暂停/取消的恢复语义。

Journal replay 的确定性假设

Journal replay 假定脚本每次执行都产生相同的调用输入。为此，常见的不确定性来源在工作流脚本内会抛 TypeError：Date.now()、Math.random()、无参 new Date()、以及作为函数调用的 Date()。时间戳与随机量应通过 args 传入（如 args.startedAt），墙钟时间在工作流返回后再加盖。new Date(explicitValue)、Date.parse(...)、Date.UTC(...) 仍合法。retry() 的墙钟计时用一颗隐藏的宿主时钟，豁免于确定性禁令，因为它绝不喂入调用 key——每次 attempt 是独立的 journaled 调用，attempt 编号是 journal key 的一部分，故确定性 replay 仍成立：成功的 attempt 在 resume 时跳过，失败的 attempt 重跑。

Resume 策略

Resume 对 paused、interrupted、failed 的 run 重放同一段 JavaScript。稳定调用身份加出现序号从 journal 取回已完成调用，已提交的 agent 调用通过其 Servitor run id 重新挂接，失败调用在同一稳定身份下重跑。succeeded、cancelled、superseded 阻止再执行，保持终态；failed 仍可 resume 以便恢复。max_calls 预算按 journal 大小种子化，resume 不发放新预算，重放 journaled key 免费。JavaScript VM 本身不序列化；中断前已完成的 command 被缓存，而中断时 controller 进程可能在 resume 时再次执行 command，故有副作用的 command 必须自带幂等检查。inspect 暴露 resume_count，终态 run summary 显示同一计数。

状态机

一个 run 处于以下状态之一：

running | waiting_human | pausing | paused | cancelling | succeeded | failed | cancelled | superseded

其中 superseded 与 failed/cancelled 相区别：当方向本身错了，supersede 把整个 run 标记为终态 superseded，并把 {reason, evidence?, newContract?} 记入 state，controller 读取 get 的 status=superseded 后写 supersede-chain 说明并另起一个新 run——这是 continue-as-new，绝不就地改脚本。waiting_human 是 gate 暂停点，controller 收集到人类值后用 approve RUN_ID --reason TEXT --value '<JSON>' 注入，get 返回该存储值。

预算与边界审计

servitor-workflows 把「能花多少」和「能碰什么」都做成可持久化、可回放的事实：预算记入 budget.jsonl，边界记入 boundary.jsonl。两者都随 run 存活，resume 不会凭空赠送额度，replay 也不会重复计费。

预算账本

每个 run 拥有一个跨整棵 workflow 树共享的多维预算账本，持久化在 budget.jsonl 中，核算 call count、可选 money 与 token 用量。

  • max_calls 是整棵 workflow 树共享的硬上限，CLI 通过 --max-calls 设置，默认 1000。每一次 host 调用——agent、command、gate 以及子 workflow——都消耗它。
  • meta.moneyCap 以 cents 为单位，可选，默认无限。只有当 contract 显式给出时，它才成为硬上限。
  • Token 用量仅用于归因（attribution），永远不会停止一个 run；不存在 token limit。
  • 记账模型为 reservation → settlement → release。在 reservation 之后、settlement 之前崩溃，既不会双扣，也不会丢失预留。resume 不发放新额度，replay 永不重复计费。

边界审计

一个 contract 可以预先声明自己的可观测写面：

export const meta = {
  name: "chain",
  contract: "workflow",
  boundary: {
    readPaths: ["."],
    writePaths: ["./out"],
    network: "allow",
    environment: { allow: ["EVIDENCE"] },
  },
};

host 对每一条 command 都按此声明进行审计，并把证据记录到 boundary.jsonl。下列情况记为 violation 并阻断 success：未声明的写、过度的环境继承，以及子 workflow 放宽权限。子 workflow 只能收紧（tighten）继承来的边界，永远不能放宽（widen）。

需要强调：这是审计边界，而非 OS 沙箱——它观察并记录，不在内核层级做隔离。isolation 层级有 none、worktree、process，以及显式请求的 container；其中 worktree 隔离产出 patch/commit 证据，同样不是安全沙箱。

关于凭据：journal 永不存储凭据值。密钥本体通过 allowlist 的环境变量穿越边界，并在 journal 中被脱敏（redacted），因此 boundary.jsonl 与 journal.jsonl 都不会泄漏 secret bodies。

CLI 速查

两个工具都是 Rust 二进制，默认 JSON 输出，统一使用 agent-native envelope {ok,data,meta,error}。所有错误都走 stdout 的同一 envelope，便于代理解析单一流。退出码：servitor 为 0 ok、1 运行失败、2 输入无效、3 未找到；servitor-workflows 多一个 4 wait 超时，且 get --wait 命中 waiting_human 时也返回 3。

servitor

传输层：一次请求 → 一个 provider 进程 → 持久化证据 → 返回类型化结果。

# 提交并立即拿到持久化句柄
servitor submit --prompt-file task.md --cwd D:\AgentWork
servitor submit --dry-run --prompt "validate fields only"

# 读取或等待（不改运行）
servitor get RUN_ID
servitor get RUN_ID --wait 120

# 盘点与清理
servitor list --limit 20 --state running
servitor gc              # 干跑报告卡住的 run
servitor gc --apply      # 把卡住的 worker 终结为 failed

# 唯一会请求终止进程的控制器操作
servitor cancel RUN_ID
servitor cancel RUN_ID --dry-run

# 传输证据与 provider 能力查看
servitor inspect RUN_ID
servitor inspect capabilities
servitor doctor
servitor schema
servitor completions powershell

# 通过 NewAPI 的图像生成/编辑传输
sigil env run L1UYUN_NEWAPI_API_KEY -- servitor image \
  --prompt-file prompt.md --out output.png

全局选项 --output human|json|quiet。委派 worker 形如 servitor submit --agent codebuddy --model hy3 ...（hy3 是 CodeBuddy 内置免费模型 id）。无 advisor 子命令；专家咨询是经 submit --model ... --system-prompt ... 表达的角色。安装须 cargo install --path . --force，使 servitor 与 servitor-worker(.exe) 落在同一 Cargo bin 目录；运行中（activity=working）勿覆盖 worker。

servitor-workflows

编排层：动态工作流、并发、命令、human gate、持久化状态、重放/暂停/取消、机器运行证据。执行契约三原语 agent + command + gate。

servitor-workflows run WORKFLOW.js [--args JSON] [--max-parallel N] [--max-calls N] [--detach]
servitor-workflows check WORKFLOW.js
servitor-workflows resume RUN_ID
servitor-workflows get RUN_ID [--wait [--timeout-seconds N]]
servitor-workflows list [--limit N] [--status STATUS]
servitor-workflows approve RUN_ID --reason TEXT [--value JSON]
servitor-workflows reject RUN_ID --reason TEXT
servitor-workflows pause RUN_ID [--dry-run]
servitor-workflows cancel RUN_ID --reason TEXT [--dry-run]
servitor-workflows supersede RUN_ID --reason TEXT [--evidence PATH] [--new-contract TEXT] [--dry-run]
servitor-workflows inspect RUN_ID
servitor-workflows watch RUN_ID
servitor-workflows schema

输出模式 --output json|human|quiet，watch 还支持 --output jsonl。run --detach 做相同校验、建一条 run 记录、启动一个脱离控制台的子进程，并立即返回 run_id 与 journal_path，绝不创建第二条 workflow run；用 get RUN_ID --wait 每 500 ms 轮询。退出码 0/1/2/3/4，错误同 envelope。

check 不运行即校验：meta 声明 + 在精确引擎包裹下解析脚本；run 复用该校验，不可解析则 2 退出且不建 run 目录。cancel 必须带 --reason，记入 state.json 为 error: "cancelled: <reason>"。恢复策略：succeeded|cancelled|superseded 阻止重跑，failed 仍可恢复。max_calls 预算从 journal 大小种子，重放不另发预算。默认 max_parallel = min(16, available_parallelism)、max_calls = 1000。

servitor-workflows run ...\goalchain.workflow.js \

设计理念

为什么用沙箱 JavaScript，而不是静态 DAG

servitor-workflows 的执行契约只有三个原语：agent + command + gate。工作流用沙箱化的 JavaScript 编写，理由很直接：普通的循环、分支、动态 fan-out，在 JavaScript 里写比在静态 DAG 里清晰得多。Rust 二进制内嵌了 Boa 引擎，Node、Deno、V8、Python 都不是运行时依赖。

脚本本身没有直接的文件系统或进程 API——一切外部工作必须穿过有类型的 agent、command 或 gate 边界。这套设计把“编排逻辑”和“实际副作用”彻底分开：逻辑写在 JS 里自由组合，副作用只在三个边界上发生并被记入日志。

为什么传输层只做一次调用

servitor 刻意停在“一次持久的 provider 调用”。它接收一个请求、运行一个 provider 进程、捕获持久证据、返回一个小的类型化结果。多步执行、fan-out、命令、人工 gate、replay/resume、验收、机器运行证据——这些都交给 sibling 工具 servitor-workflows，不属于传输层。

这条边界让职责清晰：servitor 不感知 workflow 阶段和报告策略，journal 里存的是稳定的调用身份和 Servitor run id；resume 时复用已完成的调用，而不是让传输层再提交一遍。面向读者的交付报告由 workflow 的 reporting stage 产生，不是传输层渲染的。

为什么 maker/checker 用独立子 run

独立的审查不是靠“换个 prompt”实现的，而是结构性的：reviewer 作为一个 child workflow 运行，拥有自己的 run id、journal 和边界。child 只能继承并收紧父级的 budget、boundary、capabilities、isolation，绝不能放宽。

因为 reviewer 跑在单独的 run 里，maker 选用的模型在 reviewer 的 run 里根本不是候选——maker 的模型选择永远不会成为 reviewer 的自评对象。maker/checker 的独立性是结构性的，不是 prompt 层面的约定。

能力路由：显式，不静默替换

契约可以声明显式的 provider/model 候选和 role 要求（如 maker 需要 reasoning 能力、effort: high、一定 contextTokens）。路由是基于能力的、可解释的。一个显式的 provider/model 选择永远不会被静默替换；一个不可接受的选择会在传输提交之前就失败，而不是去探测某个 provider 或制造一个 fallback。child 继承声明的候选集，且只能收窄。
