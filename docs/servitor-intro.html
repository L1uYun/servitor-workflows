Servitor 与 servitor-workflows

本地 agent 进程的 Rust 传输层 与 其之上的 工作流编排层

Servitor 是一个 Rust 传输层：接收一个请求，启动一个 provider 进程，留存可追溯的证据，返回一个小的、有类型的结果。它有意止步于「一次持久的 provider 调用」。

servitor-workflows 是 Servitor 之上的 Rust 编排层，负责动态工作流执行、并发、命令、人工 gate、持久化状态、replay/resume 与机器运行证据。

二者分工清晰：传输只管一次可靠的调用，编排只管多步与策略。

这两个工具是什么

servitor 是一个用 Rust 写的本地 agent 进程传输层。它的边界非常窄，只负责一件事：接受一个请求，启动一个 provider 进程，捕获持久的证据，然后返回一个小型的 typed 结果。工作流策略、任务分发（fan-out）、角色划分、advisor 提示、schema 校验、Git 交付、任务验收——这些都不属于 servitor，而是属于它之上的层级。

它解决的问题很具体：把“调用一个本地 agent/provider”这件事变成一次可观测、可取证、可重读的持久操作。每次 run 都会在 D:\AgentWork\state\servitor\runs/<RUN_ID>/ 下留下 request.json、record.json、stdout.txt、stderr.txt；JSON 是默认输出，统一走 {ok,data,meta,error} 信封，错误也留在 stdout，agent 只需解析一条流。它故意停在“一次 durable provider 调用”这里就不再往下走了——多步执行、重放/恢复、人工 gate、验收这些留给兄弟工具 servitor-workflows。

servitor-workflows 是构建在 servitor 之上的 Rust 动态工作流运行时。servitor 只管“一次 provider 调用”，而 servitor-workflows 负责“把多次调用组织成一条可恢复的链”：动态工作流执行、并发、命令、人工 gate、持久状态、重放（replay）、暂停、取消，以及机器运行证据。面向读者的交付报告则是工作流产物，不由 Rust 运行时直接渲染。

它的执行契约只有三个原语：agent + command + gate。工作流用沙箱化的 JavaScript 编写（Boa 解释器内嵌在 Rust 二进制里，不依赖 Node/Deno/V8/Python），因为普通的循环、分支、动态 fan-out 在 JS 里比静态 DAG 更清晰。JS 脚本本身没有直接的文件系统或进程 API，所有外部动作都必须穿过有类型的 agent、command 或 gate 边界。

一句话概括分工：servitor 是“一次可靠的单次调用”，servitor-workflows 是“把多次调用编排成可恢复、可审计、带预算与边界的工作流”。前者是传输，后者是编排，两者用同一套协议类型和 Rust 实现衔接。

职责边界：谁拥有什么

两个工具是分层关系：servitor 是 Rust 传输层，只负责一次 provider 调用的提交、捕获与返回；servitor-workflows 是其上方的 Rust 编排层。README 明确把多步执行、fan-out、命令、人工 gate、replay/resume、接受与机器运行证据交给 workflows，而把 agent 进程的提交、检查、取消、输出去留给 servitor。下表按“拥有 / 刻意不拥有”两侧对照。

维度 servitor（传输层） servitor-workflows（编排层）
拥有的能力
  • agent 进程提交：servitor submit，接受一个请求、跑一个 provider 进程。
  • 检查：get、list、inspect、inspect capabilities、doctor、schema。
  • 取消：cancel 是唯一请求进程终止的控制器操作。
  • 持久化证据：每个 run 存 request.json / record.json / stdout.txt / stderr.txt。
  • provider 适配：pi（默认与设计中心）、codex、codebuddy、claude；通过 NewAPI 的 Rust 图片生成/编辑 servitor image。
  • SDK 操作：submit、get、cancel、inspect、list_runs、gc_runs。
  • 动态工作流执行（沙箱化 JavaScript，内嵌 Boa）。
  • 并发、command()、人工 gate()、retry()、supersede()、子 workflow()。
  • 持久化状态、replay/resume、pause、cancel、机器运行证据。
  • 预算账本 budget.jsonl（调用数 / 可选 money / token 归因）。
  • 边界审计 boundary.jsonl、能力注册与路由。
  • 事件流 events.jsonl 与 watch 重建实时树视图。
刻意不拥有
  • 多步执行、fan-out、角色、advisor 提示、schema 检查、Git 交付、任务接受——“属于 Servitor 之上”。
  • 无 advisor 子命令：专家咨询只是一个 角色，通过既有传输表达，且建议只是控制器证据、绝不驱动命令/gate/部署。
  • 无生成的 launcher 源码、_DONE.txt、session 缓存、daemon、队列或隐藏兜底数据库。
  • 不感知 workflow 阶段与报告策略；不渲染面向读者的报告。
  • 不含 provider 适配器：agent 进程提交/检查/取消/输出由 servitor 拥有。
  • 不静默重试 provider、不回退到别的 provider、不设 token 预算停跑（token 仅用于归因、永不停跑）、无 provider 专用文本剥离器。
  • 显式 provider/model 选择不会被静默替换；不可接受的选择在传输提交前即失败，不探测 provider、不制造兜底。
  • 不渲染面向读者的交付报告：run-summary.html 是机器运行证据，交付 HTML 由 workflow 报告阶段用 reader-centered-reporting + l1uyun-surface 产出。
状态与恢复 默认 D:\AgentWork\state\servitor\，可用 SERVITOR_STATE_ROOT 覆盖；running 时上报 2 秒 worker 心跳与进程存活 activity.status=working|stale。 默认 D:\AgentWork\state\servitor-workflows，可用 SERVITOR_WORKFLOWS_STATE_ROOT 覆盖；resume 复用 journal 中已完成调用、重连 Servitor run id、重跑失败调用，succeeded|cancelled|superseded 阻止重跑。

一句话记忆：servitor 负责“一次耐用 provider 调用”，servitor-workflows 负责“在这之上把多次调用组织成可恢复、有预算、有边界、有人工 gate 的工作流”。两者各自清楚边界，绝不互相越界。

三个执行原语

servitor-workflows 的执行契约只有三个原语：

agent + command + gate

工作流用沙箱化的 JavaScript 编写，因为普通的循环、分支和动态扇出在那里比在静态 DAG 中更清晰。Rust 二进制内嵌了 Boa 引擎；Node、Deno、V8 和 Python 都不是运行时依赖。关键约束是：JavaScript 没有直接的文件系统或进程 API——所有外部工作都必须穿过下面这三类有类型的边界。

agent(prompt, options?)

提交一次模型调用并返回经过 schema 校验后的 JSON。默认 agent 是 pi；为 pi 指定模型时使用 provider/model-id 格式（例如 "newapi/glm-5.2"），provider 前缀必须匹配 ~/.pi/agent/models.json 中 providers 的某个键，否则裸 model id 会让 pi 猜测上游 provider 并失败。典型用法：

const found = await agent("Find files to audit.", {
  schema: {
    type: "object",
    required: ["files"],
    properties: {
      files: { type: "array", items: { type: "string" } },
    },
  },
});

当 agent 调用请求结构化输出时，运行时从自由文本中抽取 JSON：剥除 reasoning 包装 → 收集候选（整段文本、fenced ```json、平衡的 {...}/[...] 区间）→ 修复尾逗号 → 按 schema 的 type 做形状过滤 → schema-valid 选择（required/properties/items）。若多个候选都校验通过，取最后一个（final-answer 约定）。schema 是候选之间的选择标准，而不只是对首个形状匹配项的事后检查。

若成功的 transport 输出仍通不过 schema 校验，引擎会在同一个逻辑 journal call 下提交恰好一次 correction request，带上原始任务、schema、校验错误和有界无效输出摘录，要求返回裸的修正 JSON；backend、model、cwd、system prompt、timeout、native args 保持不变。provider/timeout/worker/submission/inspection/cancellation 等传输层失败不会被该机制重试。结构化输出支持刻意收窄的 JSON Schema 子集：type、required、properties、items。Agent options 的真实字段包括 label、agent、model、cwd、systemPrompt、timeoutSeconds、nativeArgs、schema。

command(program, args?, options?)

运行一个本地命令并返回结构化的 CommandResult。Command options 的真实字段是 label、cwd、timeoutSeconds、env。在 Windows 上，command 子进程创建时不带控制台窗口；stdout 和 stderr 各保留有界的 1 MiB 尾部。

await retry(() => command("pwsh", ["-File", "flaky.ps1"]), {
  maxAttempts: 3,
  delayMs: 2000,
  backoff: 2,
  wallTimeSeconds: 60,
  nonRetryable: ["validation"],
});

command() 解析为结构化的 CommandResult：

{
  "argv": ["pwsh", "-NoProfile", "..."],
  "cwd": "D:\\AgentWork",
  "exitCode": 0,
  "stdout": "...",
  "stderr": "...",
  "stdoutTruncated": false,
  "stderrTruncated": false,
  "timedOut": false,
  "durationMs": 751
}

同一个对象在成功、非零退出和超时情况下都会被原子地持久化到 state/servitor-workflows/runs/<run_id>/commands/<key>/result.json。直接消费这些有类型字段；不要重新读控制台输出或加一个 "read-results" 阶段。stdout/stderr 是有界尾部，不是业务结论——如果一个 worker 必须回传机器裁决，它应该在约定路径写一个显式的 evidence JSON。

gate(question, options?)

暂停运行，等待一个人类决策。除了 yes/no，gate 还能为"人类修正输入"的情形携带一个注入值：

const fixed = await gate("give the correct contractPath", {
  expect: "value",
  current: { contractPath: "old.md" },
  hint: "should be under surveys/",
});
await command("pwsh", ["-File", "check.ps1", fixed.value.contractPath]);

运行停在 waiting_human，expect/current/hint 记录在 waiting_gate 中。收集这个值（一个聊天回答、一个本地决策页）是 controller 的工作；用 approve RUN_ID --reason TEXT --value '{"contractPath":"surveys/new.md"}' 注入，get 会返回已存储的值。

三者之外的边界

这三个原语是工作流脚本与外界交互的唯一通道。因为 JavaScript 没有直接的文件系统或进程 API，任何读文件、跑命令、问人的动作都必须分别穿过 agent、command 或 gate 的有类型边界——这样每一次外部调用都会被 journal 记录、可被 replay 复现、并受 budget 与 boundary 审计约束。parallel、pipeline、retry、workflow 等控制流原语都是围绕这三类边界调用的编排，本身不引入新的外部能力。

控制流原语

servitor-workflows 用沙箱化的 JavaScript 表达控制流，因为普通循环、分支和动态 fan-out 在脚本里比静态 DAG 更清晰。执行契约只有三个原语：agent + command + gate。除直接调用外，运行时还提供以下组合原语。

pipeline(items, ...stages)

对一组条目按一个或多个 stage 顺序串联处理，常用于动态 fan-out 场景，例如把 agent 发现的文件列表逐个送入审计调用。

phase("audit");
const results = await pipeline(
  found.files,
  file => agent(`Audit ${file}.`, { label: file }),
);

parallel(promises)

并发执行一组 promise，与 pipeline 一起覆盖「并行同构任务」与「流水线分阶段」两种结构，共同受运行树共享的并发调度器与预算账本约束。

retry(fn, options?)

对任意 agent/command thunk 做有界重试。每次尝试都是一条独立的 journaled call（尝试序号是 journal key 的一部分），因此确定性重放仍然成立：成功的尝试在 resume 时被跳过，失败的尝试重新运行。retry() 的墙钟计时使用一个被豁免于确定性禁令的隐藏宿主时钟，因为它从不进入 call key。

选项（均来自 README）：

  • maxAttempts：固定的尝试次数上限。
  • delayMs：首次回退延迟。
  • backoff：倍数（1 为固定间隔）。
  • wallTimeSeconds：总耗时上限（SLA），即使剩余尝试次数也会停止。
  • nonRetryable：当错误文本匹配时立即失败、不再重试。
await retry(() => command("pwsh", ["-File", "flaky.ps1"]), {
  maxAttempts: 3,
  delayMs: 2000,
  backoff: 2,
  wallTimeSeconds: 60,
  nonRetryable: ["validation"],
});

gate(question, options?)

暂停运行以等待人工决策。除 yes/no 外，gate 还可以为「人工修正输入」的场景携带一个注入值：把 expect 设为 "value" 以请求一个 JSON 值而非布尔，并用 current 给出当前值、hint 给出提示。运行停靠在 waiting_human 状态，expect/current/hint 记录在 waiting_gate 中；收集该值是 controller 的工作，通过 approve RUN_ID --reason TEXT --value '{...}' 注入，get 返回已存储的值。

const fixed = await gate("give the correct contractPath", {
  expect: "value",
  current: { contractPath: "old.md" },
  hint: "should be under surveys/",
});

supersede(options)

当方向本身错误时，把整个 run 标记为终态 superseded（区别于 failed/cancelled），并记录 {reason, evidence?, newContract?} 到 state。controller 读取 get 得到 status=superseded，写下 supersede-chain 说明，然后启动一个新 run——其 readiness gate 会跳过已产出的产物。这是 continue-as-new，而不是就地修改脚本。CLI 等价物：supersede RUN_ID --reason TEXT [--evidence PATH] [--new-contract TEXT]。

workflow(path, args?, options?) — 子工作流

把另一个工作流脚本作为当前 run 的子 run 运行。子 run 形成一棵持久化的结构化并发树：每个子 run 拥有自己的 run id、journal 与边界，同时共享根的并发调度器与预算账本；子 run 的结果持久化在树中并计入共享预算。

来自 README 的关键规则：

  • 子 run 继承父 run 的预算、边界、能力与隔离，且只能收紧、不能放宽。
  • 子 run 失败只会 reject 那一次 workflow() 调用；策略（catch、retry 或 fail the chain）由父脚本决定。
  • 人工等待会沿树可见地上冒：批准根 run 即可恢复等待中的后代。
  • 循环与无界递归在任何 dispatch 之前被拒绝。
  • 取消从父 run 传播到所有存活后代。

这正是表达「独立审查」的方式：审查者作为子工作流运行、带有自己收窄（只读）的边界，因此制作者的产物不会在同一个 run 中被自评。

const review = await workflow("review.workflow.js", {
  contractPath,
  evidencePath,
});

一个真实可运行的示例

上一节讲了三原语 agent + command + gate 和沙箱化 JavaScript 的执行模型。这一节直接看一段来自 README 的真实工作流脚本 audit-routes，再把它跑起来。它把上面三原语里最常用的 agent（带 schema 结构化输出）与 pipeline（动态扇出）串成一条线：先发现要审计的文件，再对每个文件做一次审计，最后返回结果数组。

脚本：audit-routes

每个工作流都必须声明 meta.contract: "workflow"。一个 run 如果省略 contract 或给出任何其他值，会在创建 run 目录之前就被拒绝。phase(name) 标记当前阶段；agent(prompt, options?) 发起一次经由 servitor transport 的 provider 调用；pipeline(items, ...stages) 对每个 item 依次跑给定的 stage，是比静态 DAG 更清晰的动态扇出方式。 

export const meta = {
  name: "audit-routes",
  contract: "workflow",
};

phase("discover");
const found = await agent("Find files to audit.", {
  schema: {
    type: "object",
    required: ["files"],
    properties: {
      files: { type: "array", items: { type: "string" } },
    },
  },
});

phase("audit");
const results = await pipeline(
  found.files,
  file => agent(`Audit ${file}.`, { label: file }),
);

return results;

这里 schema 用的是工作流契约支持的精简 JSON Schema 子集：type、required、properties、items。runtime 会从模型自由文本里提取 JSON（剥掉 reasoning 包装 → 收集候选 → 尾逗号修复 → 按形状过滤 → schema 合法性选择），多个候选都合法时取最后一个（final-answer 约定）。label 给这次 agent 调用一个可读标签，方便在 journal 和 watch 视图里辨认。

跑起来

README 给出的真实运行命令是对仓库自带的示例脚本直接执行：servitor-workflows run 会在创建 run 目录之前先做一次和 check 相同的校验（meta 声明 + 在真实引擎封装下解析脚本），脚本解析失败会以 exit 2 拒绝。校验通过后创建一个 run 记录并开始执行，get RUN_ID --wait 可以每 500ms 轮询直到成功、终态失败、取消、被取代，或停在 waiting_human。 

servitor-workflows run D:\AgentWork\tools\servitor-workflows\examples\dynamic.workflow.js

想给脚本传参，用 --args 传一段 JSON；它会在脚本里以全局 args 出现。下面是 README 里的两体协商 canary，同样是对真实示例脚本 negotiate-2body.workflow.js 的脚本组合调用： 

servitor-workflows run D:\AgentWork\tools\servitor-workflows\examples\negotiate-2body.workflow.js `
  --args '{"topic":"pick a 30s local canary","maxRounds":2}'

默认 max_parallel = min(16, available_parallelism)、max_calls = 1000（共享硬上限，覆盖整棵工作流树，可用 --max-calls 覆盖）。每个 run 自带 run-summary.html 这份机器运行证据（由 Rust 从持久化的 state 和 journal 生成，不打开浏览器），它不是面向读者的交付报告。

持久化与恢复

servitor-workflows 把每个 run 的全部可观察状态落在磁盘上，使得“杀掉控制器进程再重启”等价于一次续跑，而不是丢失工作。默认状态根是 D:\AgentWork\state\servitor-workflows，可用 SERVITOR_WORKFLOWS_STATE_ROOT 覆盖。

每个 run 的文件结构

每个 run 拥有目录 runs/<RUN_ID>/，其下固定落盘这些文件：

  • workflow.js — 本次运行的工作流脚本本体，原样留存以便 resume 时重放同一段 JavaScript。
  • state.json — 运行状态机当前值。例如 cancel 要求 --reason，该文本以 error: "cancelled: <reason>" 形式记入 state.json 供审计。
  • journal.jsonl — 稳定调用身份与调用结果日志。一次调用由“身份 + 出现序号”定位；已结算的调用在 resume 时直接取回，不必重新提交。
  • events.jsonl — 版本化、append-only 的事件流，记录每一次生命周期迁移、调用、gate、预算变动与 boundary 事件。watch 完全从该文件重建整棵运行树的实时视图，不依赖任何内存状态。
  • budget.jsonl — 多维预算账本，按 reservation → settlement → release 记账；崩溃在 reservation 与 settlement 之间既不重复计费也不丢失预留。
  • boundary.jsonl — boundary 审计证据：每条命令对照声明的读/写/网络/环境面被核对，未声明的写、过量环境继承、子任务越权都会被记为 violation 并阻止成功。凭据值从不进 journal，secret 经 allowlisted 环境变量传递并在 journal 中脱敏。
  • run-summary.html — 每个 terminal run 自带的机器运行证据页，由 Rust 从持久化状态与 journal 生成，从不打开浏览器。它是 machine run-evidence，不是面向读者的交付报告。
  • pause.request / cancel.request — pause 与 cancel 的请求落盘文件，支撑控制信号在进程边界之外传递。

Journal replay 的确定性假设

journal replay 假定脚本在每次执行中产生相同的调用输入。因此常见非确定性来源在工作流脚本内直接抛 TypeError：Date.now()、Math.random()、无参 new Date()、以及作为函数调用的 Date()。时间戳与随机量应由 args 传入（如 args.startedAt），墙钟时间在工作流返回后再盖戳。new Date(explicitValue)、Date.parse(...)、Date.UTC(...) 仍然合法。

Resume 语义

resume 重放同一段 JavaScript，对 paused、interrupted、failed 的 run 生效。稳定调用身份加出现序号从 journal 取回已完成调用，并通过 Servitor run id 重连已提交的 agent 调用；已结算的调用不会被重新提交，失败的调用在同一个稳定身份下重跑。succeeded 与 cancelled 保持 terminal，resume 只对齐它们的 terminal 产物；superseded 同样阻止重执行。JavaScript VM 本身不被序列化。inspect 暴露 resume_count，terminal run summary 显示同一计数。一条在打断前已完成的命令会被缓存；一条在控制器进程存活期间被打断的命令可能在 resume 时再执行一次，因此有副作用的命令必须自带幂等检查。

watch 从 events.jsonl 重建

servitor-workflows watch RUN_ID（或 --output jsonl watch RUN_ID）仅从持久化的 events.jsonl 重建运行树视图——状态、活跃 phase、预算/用量、等待类别、critical path、恢复命令——没有任何内存状态。被杀并重启的控制器能从事件重建出完全相同的树，并从第一个未完成调用处续跑。畸形或撕裂的事件尾在重建时被拒绝；仅最后一行撕裂作为崩溃痕迹被容忍。

状态机

一个 run 的状态取值：running | waiting_human | pausing | paused | cancelling | succeeded | failed | cancelled | superseded。其中 supersede 是“方向本身错了”的独立终态，与 failed/cancelled 区分，记录 {reason, evidence?, newContract?}；它是 continue-as-new，从不就地改脚本。resume 策略：succeeded|cancelled|superseded 阻止重执行，failed 仍可 resume 以做恢复。

预算与边界审计

servitor-workflows 用两套独立机制把“一个工作流能花多少、能碰什么”变成可审计的持久事实：一套是多维预算账本，一套是边界声明审计。两者都落到 state 下的 .jsonl 文件里，崩溃与恢复都不会破坏记账的正确性。

预算（Budget）

每个 run 拥有一份共享的多维预算账本，持久化到 budget.jsonl，跨整棵工作流树（含子工作流）统一记账。账本覆盖三类维度：

  • 调用次数 max_calls：整棵工作流树的共享硬上限，默认 1000，可用 CLI --max-calls 覆盖。每一次宿主调用——agent、command、gate 以及子工作流 workflow()——都消耗它。
  • 金钱 meta.moneyCap：可选，单位是 cents（分），默认无限制。只有当契约显式给出时，它才成为硬上限。
  • Token 用量：仅用于归因（attribution），永不停止一个 run。系统不存在 token 上限。

记账流程是 reservation → settlement → release（预留 → 结算 → 释放）。在预留之后、结算之前发生崩溃，既不会重复扣费，也不会丢失预留。恢复（resume）不会授予新的容量，重放（replay）也绝不二次计费——重放已记录在 journal 中的调用键是免费的。

边界审计（Boundary audit）

一个契约可以预先声明自己的可观测写入面：

export const meta = {
  name: "chain",
  contract: "workflow",
  boundary: {
    readPaths: ["."],
    writePaths: ["./out"],
    network: "allow",
    environment: { allow: ["EVIDENCE"] },
  },
};

宿主对每一个 command 调用都按这份声明进行审计，并把证据记录到 boundary.jsonl。下列情况会被记为违规（violation）并阻断成功：

  • 未声明的写入（undeclared write）；
  • 环境变量继承越权（excess environment inheritance）；
  • 子工作流试图放宽权限（child permission widening）。

需要强调：这是审计边界，不是 OS 沙箱。它只观察并记录，不在内核层面进行隔离与限制。因此它依赖声明与审计来形成约束，而非依赖操作系统级的强制 confinement。

凭据安全方面，journal 永不存储凭据值本身。密钥本体通过 allowlist（白名单）内的环境变量传递，并在 journal 中被脱敏（redacted）处理——敏感数据只流动于受控的环境变量通道，不会落进持久化的调用记录里。

预算账本与边界审计共同构成 servitor-workflows 的“能花多少 / 能碰什么”治理层：前者用可恢复的预留-结算模型保证计费正确，后者用声明-审计模型把可观测副作用显式化，两者都以 .jsonl 的事实记录为唯一真相。

CLI 速查

两个 CLI 都默认输出 JSON，统一使用 agent-native 信封 {ok,data,meta,error}，错误也走 stdout 以便代理只解析一个流。--output 是全局选项。

servitor

servitor 是 Rust 传输层：接收一次请求，跑一个 provider 进程，落持久证据，返回一个小的类型化结果。工作流策略、扇出、角色、验收都不在 servitor 范围。

# 提交并立即拿到一个 durable handle
servitor submit --prompt-file task.md --cwd D:\AgentWork
servitor submit --dry-run --prompt "validate fields only"

# 读取（不等）或等待（不改 run）
servitor get RUN_ID
servitor get RUN_ID --wait 120

# 盘点与清理
servitor list --limit 20 --state running
servitor gc              # dry report of stuck runs
servitor gc --apply      # finalize stuck workers as failed

# 唯一会请求进程终止的 controller 操作
servitor cancel RUN_ID
servitor cancel RUN_ID --dry-run

# 传输证据与 provider 能力检查
servitor inspect RUN_ID
servitor inspect capabilities
servitor doctor
servitor schema
servitor completions powershell

# 通过 NewAPI 的 Rust 图像生成/编辑传输
sigil env run L1UYUN_NEWAPI_API_KEY -- servitor image `
  --prompt-file prompt.md --out output.png

普通委派 worker：servitor submit --agent codebuddy --model hy3 ...（hy3 是 CodeBuddy 内置免费 model id）。servitor inspect capabilities 报告 custom_models_source 与 custom_model_count（本地配置的 NewAPI 模型，独立于 agent 内置模型）。

退出码：0 ok，1 运行失败，2 输入非法，3 未找到。输出模式：--output human|json|quiet。

servitor-workflows

位于 servitor 之上的 Rust 编排层，拥有动态工作流执行、并发、commands、human gates、持久状态、replay、pause、cancellation 与 machine run evidence。执行契约三原语：agent + command + gate。

servitor-workflows run WORKFLOW.js [--args JSON] [--max-parallel N] [--max-calls N] [--detach]
servitor-workflows check WORKFLOW.js
servitor-workflows resume RUN_ID
servitor-workflows get RUN_ID [--wait [--timeout-seconds N]]
servitor-workflows list [--limit N] [--status STATUS]
servitor-workflows approve RUN_ID --reason TEXT [--value JSON]
servitor-workflows reject RUN_ID --reason TEXT
servitor-workflows pause RUN_ID [--dry-run]
servitor-workflows cancel RUN_ID --reason TEXT [--dry-run]
servitor-workflows supersede RUN_ID --reason TEXT [--evidence PATH] [--new-contract TEXT] [--dry-run]
servitor-workflows inspect RUN_ID
servitor-workflows watch RUN_ID
servitor-workflows schema
  • run --detach：做相同校验，创建一个 run 记录，对该已有记录启动一个 console-detached 子进程，立即返回其 run_id 与 journal_path，绝不创建第二个 workflow run。用 get RUN_ID --wait 每 500ms 轮询到 success / 终态失败 / cancellation / supersession / waiting_human，加 --timeout-seconds N 限定等待。
  • check：不运行即校验工作流——meta 声明加在精确 engine wrap 下解析脚本。run 做同样校验，脚本不可解析时以 exit 2 拒绝，且不创建 run 目录。
  • cancel 需要 --reason，文本记入 state.json 的 error: "cancelled: <reason>" 供审计。
  • watch 仅从持久化的 events.jsonl 重建实时树视图，无内存状态。

输出模式：--output json（机器面公开结果，默认）/ --output human / --output quiet；watch 还支持 --output jsonl。

退出码：0 ok，1 运行/终态失败，2 输入非法，3 未找到或 get --wait 到达 waiting_human，4 等待超时。错误同样走 stdout 信封。

设计理念

为什么用沙箱 JavaScript 而非静态 DAG

servitor-workflows 用沙箱 JavaScript 表达工作流，Boa 直接内嵌在 Rust 二进制里，因此运行时不依赖 Node、Deno、V8 或 Python。理由很直接：普通的循环、分支和动态 fan-out 在脚本里写比在一张静态 DAG 里拼清晰得多。工作流的执行契约只有三个原语——agent + command + gate，其余控制流交给脚本本身。

沙箱是严格的：JavaScript 没有直接的文件系统或进程 API，一切外部工作都必须穿过类型化的 agent、command 或 gate 边界。为了支撑 journal replay 的确定性假设，脚本每次执行应产出相同的调用输入，因此常见的不确定性来源——Date.now()、Math.random()、无参 new Date()、作为函数调用的 Date()——在工作流脚本里会直接抛 TypeError；时间戳和随机量要通过 args 传入，墙钟时间在 workflow 返回后再盖戳。new Date(explicitValue)、Date.parse(...)、Date.UTC(...) 仍然合法。

为什么传输层只做一次调用

servitor 刻意停在 one durable provider call：接收一个请求，跑一个 provider 进程，捕获持久证据，返回一个小型类型化结果。多步执行、fan-out、命令、人工 gate、replay/resume、acceptance 以及机器 run evidence，全部属于上层的 servitor-workflows。工作流 journal 存储稳定的调用身份和 Servitor run id，resume 会复用已完成的调用，而不是让传输层重新提交；servitor 本身对 workflow 阶段和报告策略一无所知。reader-facing 报告由 workflow 的 reporting stage 用 reporting skills 产出，传输层不渲染报告。

为什么 maker/checker 用独立子 run

独立审查不是靠提示词约定，而是结构性的。workflow(path, args?, options?) 把另一个 workflow 脚本作为当前 run 的 child 运行：每个 child 有自己的 run id、journal 和边界，同时共享根 run 的并发调度器和 budget 账本。children 继承父级的 budget、boundary、capabilities 和 isolation，且只能收紧、不能放宽；child 失败只拒绝那一次 workflow() 调用，策略由父脚本决定；人工等待会沿树可见地上浮，批准根 run 即恢复等待中的后代；循环和无界递归在任何 dispatch 之前就被拒绝；取消从父级向所有 live 后代传播。

这样 maker/checker 独立是结构保证的：reviewer 作为 child workflow 跑在自己缩窄的只读 boundary 里，maker 的输出永远不会在同一个 run 里被自评。配合能力路由，maker 选用的模型永远不会成为 reviewer 那个 run 的候选。

能力路由显式、不静默替换

契约可以显式声明 provider/model 候选与角色要求。路由是基于能力的、可解释的：一个显式的 provider/model 选择永远不会被静默替换；一个不可接受的选择会在 transport submission 之前就失败，而不是去探测某个 provider 或制造一个 fallback。children 继承声明的候选集且只能收窄。这种显式性也延伸到模型格式：为 pi 指定模型时必须用 provider/model-id 格式，provider 前缀必须匹配 ~/.pi/agent/models.json 的 providers 键；裸 model id（如 "glm-5.2""）会让 pi 按名字猜上游 provider 并以 No API key found for <guessed-provider> 失败。
